Use the Bag of Words API to add a Bow-powered chat or completion panel to your own product. Your UI creates or reuses a report, streams a completion with `fetch`, and renders Server-Sent Events as they arrive.

This guide is for internal tools, trusted admin panels, and backend-proxied production apps.

---

## What You Need

- A Bag of Words base URL — e.g. `http://localhost:3000` or `https://bow.example.com`
- A `bow_...` API key (see [Choosing a credential](#choosing-a-credential) below)
- Optional data source or agent IDs to attach to the report
- A browser or backend that can call the Bow API

<Note>
  Do **not** include `/api` in the user-facing base URL. Build the API base internally:

  ```ts
  const bowUrl = inputBowUrl.replace(/\/+$/, "").replace(/\/api$/i, "");
  const apiBase = `${bowUrl}/api`;
  ```
</Note>

### Choosing a credential

Both key types are `bow_...` keys and authenticate identically. Pick based on who owns the integration:

| Credential | Created in | Use it when |
| --- | --- | --- |
| **Service account key** | Settings → Service Accounts → _create account_, then _create key_ | The integration is owned by the organization. Recommended for anything long-lived: the key survives staff changes, carries its own org role, is separately revocable, and cannot mint further keys or manage members even if leaked. |
| **Personal API key** | Settings → API Keys | Prototyping, or a tool that should act as one specific person. The key inherits that user's permissions and dies with their account. |

Send the key either way — both are accepted on every endpoint in this guide:

```http
Authorization: Bearer bow_...
X-API-Key: bow_...
```

<Note>
  An API key already identifies its organization, so you do **not** need the `X-Organization-Id` header that browser sessions use. Sending a wrong one overrides the key's org and fails with `404 organization.not_found`.

  Service-account keys report an empty `organizations` array from `/api/users/whoami` — a service account is bound to its org through the account itself, not through a seat-consuming membership. Use `GET /api/mentions/available` as the reachability check for those keys.
</Note>

## Recommended Architecture

For a **private internal app**, the browser can call Bow directly with an API key.

For a **public app**, proxy requests through your own backend:

```text
Browser UI → Your backend → Bag of Words API
```

Your backend should store the Bow API key, enforce your app's authorization rules, and stream the Bow SSE response back to the browser. Do not expose long-lived Bow API keys in public client-side code.

---

## Allow Your Origin (CORS)

If the browser calls Bow directly, the Bow deployment must allow your page's origin. Cross-origin requests are **rejected by default** — the preflight returns `400` with no `Access-Control-Allow-Origin` header, and the browser reports `Failed to fetch`.

Set the allowed origins on the Bow server (comma-separated, no trailing slash) and restart it:

```bash
BOW_CORS_ALLOWED_ORIGINS=https://app.example.com,http://localhost:5173
```

Origins must match scheme, host, and port exactly. `Authorization`, `Content-Type`, and `X-Organization-Id` are already on the allow list, as is `Accept` (a browser-safelisted header), so the streaming request needs no extra configuration once the origin is allowed.

<Note>
  A backend proxy never hits this: server-to-server calls are not subject to CORS. Leaving `BOW_CORS_ALLOWED_ORIGINS` unset is the safe default for proxied and same-origin deployments.
</Note>

## Minimum Streaming Flow

1. Create a report with the data sources your chat should use.
2. `POST` a streaming completion to that report.
3. Parse SSE frames from the response body.
4. Render assistant text, reasoning, tool progress, and errors from the events.

<Note>
  Reports are the scope for data sources. Attach data sources when creating or updating the report — not in the completion prompt mentions.
</Note>

## Create a Report

Create a report when the user starts a new chat session or when you need a temporary scratch report.

```http
POST /api/reports
Authorization: Bearer bow_...
Content-Type: application/json

{
  "title": "Customer Support Chat",
  "data_sources": ["agent-or-data-source-id"]
}
```

```ts
async function createReport(apiBase: string, apiKey: string, dataSourceIds: string[]) {
  const response = await fetch(`${apiBase}/reports`, {
    method: "POST",
    headers: {
      Authorization: `Bearer ${apiKey}`,
      "Content-Type": "application/json",
      Accept: "application/json",
    },
    body: JSON.stringify({
      title: "Embedded Bow Chat",
      data_sources: dataSourceIds,
    }),
  });

  if (!response.ok) throw new Error(`Create report failed: ${response.status}`);
  return response.json() as Promise<{ id: string }>;
}
```

## Stream a Completion

Use `fetch`, not `EventSource`, because the completion stream is a `POST` request with custom headers.

The same endpoint serves streaming and non-streaming responses. It streams when **any** of these is true — send `stream: true` and the `Accept` header together for clarity:

- `stream: true` in the request body
- `Accept: text/event-stream`
- `?stream=true` in the query string

```http
POST /api/reports/{report_id}/completions
Authorization: Bearer bow_...
Content-Type: application/json
Accept: text/event-stream

{
  "prompt": {
    "content": "Show me the top customers this month",
    "mentions": [],
    "mode": "chat"
  },
  "stream": true
}
```

```ts
async function streamCompletion(params: {
  apiBase: string;
  apiKey: string;
  reportId: string;
  prompt: string;
  signal?: AbortSignal;
  onEvent: (event: BowSseEvent) => void;
}) {
  const response = await fetch(
    `${params.apiBase}/reports/${encodeURIComponent(params.reportId)}/completions`,
    {
      method: "POST",
      headers: {
        Authorization: `Bearer ${params.apiKey}`,
        "Content-Type": "application/json",
        Accept: "text/event-stream",
      },
      body: JSON.stringify({
        prompt: { content: params.prompt, mentions: [], mode: "chat" },
        stream: true,
      }),
      signal: params.signal,
    },
  );

  if (!response.ok) {
    const detail = await response.text();
    throw new Error(`Completion failed: ${response.status} ${detail}`);
  }

  if (!response.body) throw new Error("Streaming response body is unavailable.");

  const reader = response.body.getReader();
  const decoder = new TextDecoder();
  const parser = createSseParser(params.onEvent);

  while (true) {
    const { done, value } = await reader.read();
    if (done) break;
    parser.feed(decoder.decode(value, { stream: true }));
  }

  parser.feed(decoder.decode());
  parser.flush();
}
```

## SSE Format

Bow sends standard Server-Sent Events:

```text
event: completion.started
data: {"event":"completion.started","data":{"system_completion_id":"..."}}

event: block.delta.token
data: {"event":"block.delta.token","data":{"block_id":"...","field":"content","token":"Hello"}}

data: [DONE]
```

A blank line ends an event. Multiple `data:` lines belong to the same event and should be joined with `\n`.

The `data:` payload is an envelope — parse it like this:

```ts
const parsed = JSON.parse(dataString);
const payload = parsed.data ?? parsed;
```

`data: [DONE]` means the stream is complete.

## Tiny SSE Parser

```ts
type BowSseEvent = {
  event: string;
  payload: unknown;
  raw: string;
  receivedAt: string;
  done?: boolean;
  malformed?: boolean;
};

function createSseParser(onEvent: (event: BowSseEvent) => void) {
  let buffer = "";
  let eventName = "message";
  let dataLines: string[] = [];
  let rawLines: string[] = [];

  function dispatch() {
    if (rawLines.length === 0 && dataLines.length === 0) return;

    const dataString = dataLines.join("\n");
    const raw = `${rawLines.join("\n")}\n\n`;
    const receivedAt = new Date().toISOString();

    if (dataString === "[DONE]") {
      onEvent({ event: "[DONE]", payload: "[DONE]", raw, receivedAt, done: true });
    } else {
      try {
        const parsed = JSON.parse(dataString);
        onEvent({ event: eventName, payload: parsed.data ?? parsed, raw, receivedAt });
      } catch (error) {
        onEvent({
          event: eventName,
          payload: { error: String(error), data: dataString },
          raw,
          receivedAt,
          malformed: true,
        });
      }
    }

    eventName = "message";
    dataLines = [];
    rawLines = [];
  }

  return {
    feed(chunk: string) {
      buffer += chunk;

      while (true) {
        const newlineIndex = buffer.search(/\r\n|\n|\r/);
        if (newlineIndex === -1) break;

        const line = buffer.slice(0, newlineIndex);
        const newline = buffer.slice(newlineIndex).match(/^\r\n|\n|\r/)?.[0] ?? "\n";
        buffer = buffer.slice(newlineIndex + newline.length);

        if (line === "") { dispatch(); continue; }

        rawLines.push(line);
        if (line.startsWith(":")) continue;

        const colonIndex = line.indexOf(":");
        const field = colonIndex === -1 ? line : line.slice(0, colonIndex);
        const value = colonIndex === -1 ? "" : line.slice(colonIndex + 1).replace(/^ /, "");

        if (field === "event") eventName = value || "message";
        if (field === "data") dataLines.push(value);
      }
    },
    flush() {
      if (buffer) { rawLines.push(buffer); buffer = ""; }
      dispatch();
    },
  };
}
```

## Event Reference

Handle unknown events gracefully — the API may add events over time. A minimal chat only needs `completion.started`, `block.upsert`, `block.delta.token`, `block.delta.text`, the `tool.*` events, and `completion.finished`; the rest are available when you want to render more of the run.

Every frame carries the same envelope — `event`, `data`, `timestamp`, `completion_id`, `agent_execution_id`, `seq` — so `seq` gives you a stable ordering within a run.

### Run lifecycle

| Event | Meaning | UI suggestion |
| --- | --- | --- |
| `completion.started` | The run has started. `data` carries `system_completion_id`, `user_prompt`, and the resolved `model` | Mark the chat as streaming and store `system_completion_id` — you need it to resume or stop the run |
| `completion.resumed` | Sent first on a re-attached stream instead of `completion.started` | Treat exactly like `completion.started` |
| `instructions.context` | The instructions loaded into this run's context | Optional; useful for a "what did the agent know" debug panel |
| `completion.follow_ups` | Suggested next questions, sent after the answer | Render as clickable chips |
| `completion.finished` | The run finished. `data.status` is `success`, `error`, or `stopped` | Mark the chat done. **May arrive more than once** for a single run — make this handler idempotent and ignore repeats |
| `completion.error` | The run failed at the completion level | Stop streaming and show the error message |
| `llm.error` | The LLM provider or model call failed | Stop streaming and show the error message |
| `[DONE]` | The SSE stream ended | Close the stream and re-enable input |

### Text and blocks

| Event | Meaning | UI suggestion |
| --- | --- | --- |
| `block.upsert` | A block was created or updated. `data.block` holds the full block, including `title`, `icon`, and `status` | Insert or update the matching assistant, reasoning, or tool block |
| `block.delta.token` | A token-level delta. Always branch on `data.field` — `content` is the visible answer, `reasoning` is the thinking trace | Append `data.token` to that field |
| `block.delta.text` | A full replacement for a block field | Replace the field with `data.text` |
| `block.delta.text.complete` | That field is finished streaming | Stop any typing indicator on the block |
| `block.delta.artifact` | Incremental changes to a chart or table attached to the block | Optional; re-render the artifact preview |
| `decision.partial` | An intermediate reasoning/action decision | Show provisional reasoning or the planned tool call |
| `decision.final` | The decision was finalized. `data.metrics` carries timings and token usage | Mark the decision block complete |

### Tools and artifacts

| Event | Meaning | UI suggestion |
| --- | --- | --- |
| `tool.started` | A tool call started (`tool_name`, `arguments`, `tool_execution_id`, `block_id`) | Show a compact running tool row |
| `tool.progress` | Progress within a tool call — expect many per call | Update the tool row summary |
| `tool.finished` | A tool call finished (`status`, `result_summary`, `result_json`) | Mark the row success/error; keep result JSON behind a disclosure |
| `query.created` | The agent created a saved query on the report | Optional; link to it |
| `visualization.created` / `visualization.updated` | A chart or table was created, then filled in once the query ran | Optional; render the visualization inline |

See [Tool event payloads](#tool-event-payloads) for the exact fields these carry.

## Tool Event Payloads

The three `tool.*` events share a stable envelope; everything tool-specific lives in one field per event (`arguments`, `payload`, `result_json`). Build your UI on the envelope and treat the tool-specific field as opaque.

| Field | On | Notes |
| --- | --- | --- |
| `tool_name` | all three | e.g. `create_data`, `create_artifact`, `clarify`. New tools appear over time — never switch exhaustively on this |
| `tool_execution_id` | all three | **The correlation key.** Join `started` → `progress` → `finished` on this |
| `block_id` | all three | The block this call belongs to, so you can nest the row under the right message |
| `arguments` | `started` | Tool-specific input object |
| `payload` | `progress` | Tool-specific progress object, always with a `stage` string |
| `status`, `result_summary`, `duration_ms`, `result_json` | `finished` | See below |

<Warning>
  Key tool rows on `tool_execution_id`, not `tool_name`. A single run calls the same tool several times — a dashboard request runs `create_data` once per chart — and keying on the name collapses them into one row.
</Warning>

### `tool.started`

`arguments` is whatever that tool takes. For `create_data`:

```json
{
  "tool_name": "create_data",
  "tool_execution_id": "7cd0027a-e8e3-402a-880e-afeff6bcb8f3",
  "block_id": "e8547efa-6f51-4a33-bd42-68af0eea9676",
  "arguments": {
    "title": "Total Customers",
    "user_prompt": "Count the total number of customers in the database.",
    "interpreted_prompt": "Count the distinct number of rows in the Customer table.",
    "tables_by_source": [{ "tables": ["Customer"] }],
    "visualization_type": "count"
  }
}
```

`arguments.title` is a good label for the tool row across most tools.

### `tool.progress`

Expect a dozen or more of these per call. `payload.stage` is the only field guaranteed to be present; the rest describe that stage:

```json
{
  "tool_name": "create_data",
  "tool_execution_id": "7cd0027a-...",
  "block_id": "e8547efa-...",
  "payload": { "stage": "executing_code", "attempt": 0 }
}
```

A `create_data` call walks through stages such as `init`, `resolving_tables`, `building_context`, `generating_code`, `generated_code`, `executing_code`, `post_execution`, `inferring_visualization`, and `formatting_widget`, carrying extras like `code`, `execution_ms`, `chart_type`, and `series` along the way. Render `stage` as status text; do not branch on the exact set, which is tool-specific and grows.

### `tool.finished`

```json
{
  "tool_name": "create_data",
  "tool_execution_id": "7cd0027a-...",
  "block_id": "e8547efa-...",
  "status": "success",
  "duration_ms": 8237.999,
  "result_summary": "Created data 'Total Customers' successfully; 1 rows x 1 cols; cols: total_customers; chart: count.",
  "created_step_id": "a835fb5b-7e4a-48d7-8bc1-4f8bc239a51b",
  "created_widget_id": null,
  "created_visualization_ids": ["3f5ea153-80f2-4d6f-a417-9691f434b19e"],
  "result_json": { "success": true, "code": "...", "data": {}, "view": {} }
}
```

- **`result_summary`** is a plain-English sentence the agent writes for exactly this purpose. Render it as the tool row's collapsed label instead of parsing `result_json`.
- **`created_step_id` / `created_widget_id` / `created_visualization_ids`** link the tool call to the artifacts it produced — this is how you attach a rendered chart to the right tool row. They are `null` for tools that create nothing.
- **`result_json` is tool-specific and can be large.** For `create_data` it carries the generated Python, every executed query, and the full result rows. Keep it behind a disclosure, do not log it wholesale, and never assume a key exists.

Three tools, three unrelated `result_json` shapes — this is why it has no schema:

| Tool | `result_json` keys |
| --- | --- |
| `create_data` | `success`, `code`, `data`, `data_preview`, `data_model`, `view`, `query_id`, `executed_queries`, `execution_log`, `stats`, `errors`, timing fields |
| `create_artifact` | `artifact_id`, `title`, `version`, `mode`, `code`, `code_preview`, `artifact_preview`, `query_id`, `visualization_ids` |
| `clarify` | `status`, `query_id`, `created_visualization_ids` |

### Clarify: when the agent asks you a question

`clarify` is the one tool an embedded chat must handle explicitly. When the prompt is ambiguous the agent calls it, and the turn **ends** — `tool.finished` reports `status: "success"` with `result_json.status: "awaiting_response"`, then `completion.finished` and `[DONE]` arrive as usual. Nothing is broken; the agent is waiting on the user.

The questions are in `tool.started`:

```json
{
  "tool_name": "clarify",
  "arguments": {
    "questions": [
      { "text": "Which group are you interested in?", "options": ["VIP customers", "Best sellers", "Other…"] },
      { "text": "What would you like to see about them?", "options": ["A list or ranking", "Sales trends", "Other…"] }
    ],
    "context": "User said \"the important ones\" — need to identify which entities they want."
  }
}
```

Render the questions with their `options` as chips, then send the answers as a **new completion** on the same report — that is what resumes the work:

```json
{ "prompt": { "content": "Q: Which group are you interested in?\nA: VIP customers\n\nQ: What would you like to see about them?\nA: A list or ranking", "mentions": [], "mode": "chat" }, "stream": true }
```

Optionally persist the raw selections first, so a reload rehydrates the form instead of showing an unanswered question:

```http
POST /api/completions/{system_completion_id}/tool_executions/{tool_execution_id}/clarify_response
Authorization: Bearer bow_...
Content-Type: application/json

{ "selected_chips": ["VIP customers"], "other_texts": [], "free_texts": [] }
```

It returns `{ "ok": true, "result_json": { "status": "answered", "user_response": {...} } }` — the tool execution flips from `awaiting_response` to `answered`, which is what a re-attached stream replays.

An integration that ignores `clarify` looks like it silently gave up on ambiguous questions. If you do not want to build the form, render the question text and let the user reply in the normal chat input — the plain answer works too.

## Rendering a Chat UI

Keep the UI reducer small:

- Store `status`: `idle`, `streaming`, `success`, or `error`
- Store blocks by `id`
- Append `block.delta.token` for assistant text
- Replace text on `block.delta.text`
- Show reasoning inside a collapsible disclosure
- Show tools as compact rows keyed by `tool_execution_id`, labelled with `result_summary`
- Keep raw JSON behind a disclosure for tool payloads
- Keep the raw SSE log available in a debug tab

```ts
function applyBowEvent(state: ChatState, event: BowSseEvent) {
  const payload = event.payload as Record<string, any>;

  switch (event.event) {
    case "completion.started":
      state.status = "streaming";
      state.systemCompletionId = payload.system_completion_id;
      break;

    case "block.delta.token": {
      const blockId = payload.block_id ?? "streaming";
      const block = state.blocks[blockId] ??= { content: "" };
      if (payload.field === "content") block.content += payload.token ?? "";
      if (payload.field === "reasoning") block.reasoning = `${block.reasoning ?? ""}${payload.token ?? ""}`;
      break;
    }

    // Key on tool_execution_id — one run can call the same tool many times.
    case "tool.started":
    case "tool.progress":
    case "tool.finished": {
      const id = payload.tool_execution_id;
      if (!id) break;
      state.tools[id] = { ...(state.tools[id] ?? {}), ...payload };
      break;
    }

    case "completion.error":
    case "llm.error":
      state.status = "error";
      state.error = payload.message ?? payload.error ?? JSON.stringify(payload);
      break;

    // Both can arrive more than once — keep this branch idempotent.
    case "completion.finished":
      if (payload.status === "error") state.status = "error";
      else if (state.status !== "error") state.status = payload.status ?? "success";
      break;

    case "[DONE]":
      if (state.status === "streaming") state.status = "success";
      break;
  }
}
```

## Resume and Stop a Run

A dropped connection does not stop the agent — the run continues server-side. Two endpoints cover the rest of the lifecycle.

**Re-attach to a run in progress** (page refresh, network drop, a second tab). Pass the `system_completion_id` you stored from `completion.started`. The endpoint is idempotent and side-effect free, so it is safe to retry with backoff. It replays the run's blocks, then continues live:

```http
GET /api/reports/{report_id}/completions/{system_completion_id}/stream
Authorization: Bearer bow_...
Accept: text/event-stream
```

**Actually stop a run.** `AbortController` only closes your side of the socket; the agent keeps working and keeps spending tokens. To cancel the run itself, call:

```http
POST /api/completions/{system_completion_id}/sigkill
Authorization: Bearer bow_...
```

Wire your Stop button to both: `sigkill` to end the run, `AbortController` to release the reader. The run then finishes with `status: "stopped"`.

## Non-Streaming and History

Omit the streaming triggers and the same `POST` returns JSON once the run completes, which suits scheduled jobs and server-side summaries. Add `?background=true` to return immediately and let the run continue in the background.

Sending a second prompt while a run is still going starts a **second concurrent run** on the report. If you want the chat to behave like one turn at a time instead, send `"queue": true` — the prompt is stored with `status: "queued"` and starts automatically when the current run finishes. Queued prompts never stream; drop one with `DELETE /api/completions/{completion_id}/queued` while it is still queued.

Both that response and `GET /api/reports/{report_id}/completions` return the **whole conversation envelope**, not a single completion:

```json
{
  "report_id": "...",
  "completions": [{ "id": "...", "role": "system", "status": "success", "completion_blocks": [] }],
  "latest_completion": "...",
  "has_more": false,
  "next_before": null,
  "total_completions": 4
}
```

Read the answer from the last `role: "system"` entry. For history, page with `?limit=` and `?before=` (an ISO timestamp cursor) and follow `has_more` / `next_before`.

## Error Handling

| Status | Meaning |
| --- | --- |
| `400` | Invalid request, or no default LLM model configured — _"No default LLM model configured. Please go to Settings \> LLM and set a default model."_ |
| `401` | Missing, invalid, expired, or revoked API key |
| `403` | The key does not have permission for this resource. Also returned when a service-account key touches identity management (`/api/api_keys`, `/api/service_accounts`) — that is by design |
| `404` | Report not found, or `organization.not_found` from an `X-Organization-Id` header that does not match the key |
| Network / CORS | The browser could not reach Bow, or the origin is not in `BOW_CORS_ALLOWED_ORIGINS` |
| Abort | User stopped the stream — treat as controlled cancellation, not a crash |
| Malformed SSE | Keep the raw frame and show a debug-friendly parse error |

<Warning>
  Failures **after** the stream opens do not change the HTTP status — the response is already `200`. A run that fails mid-flight reports it as a `completion.error` or `llm.error` frame, or as `completion.finished` with `status: "error"`. Handle those events, not just `response.ok`.
</Warning>

## Production Checklist

- Proxy public integrations through your backend
- Use a service-account key, not a personal API key, for anything long-lived
- Keep Bow API keys server-side for public apps
- Set `BOW_CORS_ALLOWED_ORIGINS` if the browser calls Bow directly
- Wire the Stop button to `sigkill` **and** `AbortController` — aborting alone leaves the run going
- Persist the report ID for the conversation and the `system_completion_id` for the run in flight, so a refresh can re-attach
- Attach data sources through report creation or update
- Keep `mentions: []` unless your integration intentionally supports Bow prompt mentions
