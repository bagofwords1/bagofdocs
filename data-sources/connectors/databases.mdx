This is a reference page for the connectors that need no external app registration, tenant setting, or admin consent — just **network access from the BOW host** and a **login with read permission**. Add them under **Data Sources → Add data source**, fill in the fields below, test the connection, and pick the tables the agent may use.

Connectors with real external setup have their own pages: [Snowflake](/data-sources/connectors/snowflake), [Google BigQuery](/data-sources/connectors/bigquery), and [Microsoft SQL Server](/data-sources/connectors/sql-server).

<Note>
  Most of these support both a **shared** credential (one login for the whole workspace) and **per-user** credentials (each person authenticates as themselves). Per-user authentication on a database connector requires an Enterprise license — see [Authentication](/data-sources/authentication). Where a mode is shared-only, it is marked below.
</Note>

## Notes on specific connectors

### PostgreSQL

`sslmode` takes the libpq values `disable`, `allow`, `prefer`, `require`, `verify-ca`, and `verify-full`. Use `require` for IAM-authenticated connections such as AWS RDS, which reject unencrypted logins.

System schemas are left out of indexing. Turn on `include_system_schemas` (**Index system catalog**, off by default) to also index `pg_catalog` and `information_schema` — `pg_stat_activity`, `pg_locks`, and so on — so the agent can answer questions about the database itself.

### Stored procedures and functions

PostgreSQL, MySQL, MariaDB, and [SQL Server](/data-sources/connectors/sql-server) connections have an **Index stored procedures & functions** option (`index_routines`), off by default. With it on, BOW also indexes procedures and functions together with their source, so the agent can read their logic and may call functions inside its queries. Use a read-only database account when you turn it on.

### IBM Db2

Covers **Db2 for Linux, Unix and Windows** (including Db2 on Cloud and Db2 Warehouse) and **Db2 for z/OS**, over IBM's `ibm_db` driver. BOW detects the product on connect and reads the matching system catalog; set `platform` to `luw`, `zos`, or `ibmi` to force it instead of `auto`. The connection is read-only.

- `port` is usually `50000` on LUW and `446` on z/OS.
- `database` is the database name on LUW and the **location name** on z/OS.
- `schema` takes one schema or a comma-separated list. Leave it blank to index every non-system schema.
- Turn on `ssl` to connect over TLS, and point `port` at the server's TLS port. If the server certificate is signed by an internal CA, paste that CA as PEM text into `ssl_ca`.
- On z/OS, `user` is the RACF user ID.

<Warning>
  Db2 for z/OS needs **Db2 Connect** activated on the server; without it the server answers `SQL1598N`. Db2 LUW needs nothing extra.
</Warning>

IBM publishes no `ibm_db` build for Linux ARM64, so the connector does not appear in the catalog on BOW hosts where the driver is missing. For Db2 for IBM i, use the IBM i connector below — it needs no Db2 Connect license.

### IBM i

Connects to **Db2 for IBM i** (AS/400, iSeries) through IBM's open-source **Mapepire** server, so it needs no Db2 Connect license and no ODBC driver. Install and start Mapepire on the IBM i once:

```bash
yum install mapepire-server
sc start mapepire
```

`port` is the Mapepire port, `8076` by default. `schema` (shown as **Libraries**) takes one library or a comma-separated list; leave it blank to index every non-system library. Tables are named `LIBRARY.TABLE`.

Mapepire generates a self-signed certificate unless one is installed. With `verify_ssl` on (the default), paste that certificate, or the CA that signed it, as PEM text into `ssl_ca`; turn `verify_ssl` off only on a trusted network.

Log in with an IBM i user profile that has read-only authority to the libraries you index. Every connection also opens its IBM i job with read-only access, so the system itself refuses writes.

### DuckDB

DuckDB is not a server connection. `uris` holds either the path to a local `.duckdb` file, or **one URI pattern per line** pointing at parquet or CSV files, which BOW registers as views and queries in-process. Wildcards are supported:

```text
s3://analytics-lake/events/*.parquet
az://container/exports/2024/*/*.csv
/data/reference/dim_customer.parquet
```

Pick the auth mode matching the backing store, not DuckDB itself:

| Mode | Fields | Scope |
| :-- | :-- | :-- |
| No Auth (public/local) | — | Shared |
| AWS Keys | `access_key`, `secret_key`, `region`, `session_token` | Shared |
| GCP Service Account | `service_account_json` | Shared or per-user |
| Azure Connection String | `connection_string` (SAS or account key) | Shared |

`session_token` is only for temporary AWS credentials. Local paths and `file:/` URIs work with no auth at all.

### ClickHouse

Connects over the HTTP interface — `8123` for plain HTTP, `8443` with `secure` on (the usual setting for ClickHouse Cloud). The password cannot be blank, so create a dedicated user rather than relying on a passwordless `default`.

When `database` lists several databases, queries run against the first one; agents should qualify tables in the others as `db.table`.

ClickHouse supports [custom tables](/bow-fast/custom-queries): scheduled, locally cached query results that agents answer from instead of querying the service each time. On ClickHouse Cloud that lets an idle service stay idle — see [Cut ClickHouse Cloud costs](/bow-fast/clickhouse-cloud-costs). For that, the user needs `SELECT` on the source tables and on `system.parts` (used to estimate scan size), and `KILL QUERY` so an aborted refresh can stop its own query on the server. `Enum` columns are stored in the cached copy as their labels.

### Trino

`host` is the coordinator hostname, without `http://`. `catalog` is the only required scope: it is where queries run by default, and its tables are named `schema.table`. `schema` optionally narrows indexing to one schema or a comma-separated list; blank indexes every schema in the catalog. To let the agent join across catalogs, list the others in `additional_catalogs` — their tables are named `catalog.schema.table`.

Set `protocol` to `https` for any authenticated or TLS-enabled coordinator; the password is required over HTTPS and may be blank only for an unauthenticated coordinator over HTTP. Keep `verify_ssl` on and paste an internal CA's PEM chain into `ca_certificate` rather than turning verification off. `role` sets the role to assume for the session (blank uses the login's default role), and `timezone` sets an IANA session timezone such as `Europe/Berlin` that relative dates like `current_date` are computed in.

The **Access token (JWT)** mode takes an `access_token` and an optional session `user`; leave `user` blank to act as the token's identity.

### Starburst

**Starburst Galaxy** and **Starburst Enterprise** use the same connection as Trino, with defaults for Starburst: `port` `443` and `protocol` `https`. Starburst requires TLS for every authentication method, so keep `https`. Logins are a username and password or an **Access token (JWT)**, and `additional_catalogs` lets one connection join across several catalogs.

For **Starburst Galaxy**:

<Steps>
  <Step title="Create a role for BOW">
    In Galaxy, go to **Access control → Roles and privileges** and add a role (for example `bagofwords`). Under **Add privileges**, grant it **Use cluster** on the cluster and **Select from table** on every catalog or schema the agent should see.
  </Step>
  <Step title="Create a service account">
    Go to **Access control → Service accounts**, create one with the new role as its default role, and generate a password. The username is the service account's full name, for example `bagofwords@<account>.galaxy.starburst.io`. Enter it as `user`, with the generated password.
  </Step>
  <Step title="Copy the connection details">
    Open the cluster's **Connection info** (**Partner connect → Other clients**). `host` is `<account>-<cluster>.trino.galaxy.starburst.io` and the port is `443` over HTTPS. If the cluster restricts client IPs, allow the BOW instance's address.
  </Step>
</Steps>

For **Starburst Enterprise**, use the coordinator hostname with its TLS port (`8443` by default, or `443` behind a load balancer) and keep `protocol` on `https`. Log in with an LDAP or password-file user, or switch to **Access token (JWT)** for a JWT the coordinator's OAuth2 / JWT authenticator accepts. If the certificate comes from an internal CA, paste the CA's PEM certificate into `ca_certificate`.

Then set `catalog` and, optionally, `schema`. If the login has several roles, set `role` to the one that holds the grants — a login whose default role is restricted sees no tables otherwise.

### Teradata

`logmech` selects the logon mechanism: `TD2` for database users, or `LDAP` for directory users. `host` is the TPA or COP name of the system.

`sslmode` controls TLS:

| `sslmode` | Behavior |
| :-- | :-- |
| `DISABLE`, `ALLOW` | Teradata driver modes for connections without TLS by default. |
| `PREFER` *(default)* | Uses TLS when the server offers it, without checking the certificate. |
| `REQUIRE` | Always uses TLS. |
| `VERIFY-CA` | Also checks that the certificate is trusted. |
| `VERIFY-FULL` | Also checks that the certificate matches the host name. |

For `VERIFY-CA` and `VERIFY-FULL`, paste the certificate authority to trust as PEM text into `ssl_ca`, or leave it empty to use the system trust store. TLS connections use port `443` unless `https_port` is set in `additional_params`. `encryptdata` (on by default) encrypts data on non-TLS connections; TLS connections are always encrypted.

`additional_params` passes extra `teradatasql` driver parameters, such as `cop=false` or `coplast=true` when DNS is slow, `account`, `charset`, or `tmode`. Credentials, TLS, and encryption settings cannot be set there.

The connection is read-only: write statements, including Teradata shorthands such as `CT`, `MODIFY USER`, and `GIVE`, are refused. A query that hits the connection's timeout is cancelled on the server rather than left running on the warehouse.

### Apache Druid

Set `secure` to true for HTTPS, and adjust `port` for what you are pointing at — `8082` for a Broker, `8888` for a Router. `schema` defaults to `druid`; system schemas are always excluded from indexing.

Two token modes exist and they are not interchangeable:

- **API Token (Bearer)** sends `Authorization: Bearer <token>`.
- **API Token (Basic)** sends the `basic_token` value verbatim as `Authorization: Basic <token>`, with **no base64 encoding**. Use this one for Imply Polaris `pok_…` API keys.

### Apache Pinot

Points at the Broker SQL endpoint. `controller` is an optional controller base URL (for example `http://controller-host:9000`), used for richer metadata. `query_options` passes a Pinot `queryOptions` string through on every query — `useMultistageEngine=true` is the common one.

### MongoDB

The only document-shaped connector here: the agent sees collections and inferred document structure rather than tables and columns, and writes MongoDB queries rather than SQL.

For **Atlas**, set `use_srv` to true — the connection then uses `mongodb+srv://`, `port` is ignored, `auth_source` is ignored, and TLS is automatic. For a self-hosted deployment, leave `use_srv` off and set `tls` and `auth_source` yourself. `user` and `password` may both be blank for an unauthenticated deployment.

### Spark

Runs Spark SQL against a remote cluster over **Spark Connect** (`sc://`). Compute stays on the cluster — BOW sends SQL and receives results, with no in-process engine on the BOW server.

Leave `catalog` blank to use the session default, and `database` blank to discover all databases (it also takes a comma-separated list). `require_partition_filter` is a guardrail worth turning on for large lakehouse tables: queries that would scan a partitioned table without filtering on a partition column are rejected via `EXPLAIN` before they run.

The **No auth** mode assumes the Spark Connect endpoint is network-gated — behind a VPN or Tailscale, for example. Otherwise use a Bearer Token.

### AWS Redshift

Three auth modes, all of which still require a `user`:

| Mode | Fields | What it does |
| :-- | :-- | :-- |
| Username / Password | `user`, `password` | Ordinary Redshift database login. |
| AWS Keys (IAM) | `user`, `access_key`, `secret_key` | Authenticates with IAM credentials rather than a database password. |
| Assume Role (ARN) | `user`, `role_arn` | Assumes the named role and connects with the resulting temporary credentials, refreshed automatically before expiry. |

`region` is needed for both IAM modes. `cluster_identifier` identifies the cluster for IAM-based credential issuance. Leave `ssl_mode` at `require` unless you have a reason not to.

### AWS Athena

Athena is serverless: there is no host or port, only a `region` and a Glue `database`. `data_source` is the Athena catalog name and stays `AwsDataCatalog` for the standard Glue Data Catalog.

One connection can cover several Glue databases. In `database`, give a comma-separated list of names, globs, and `!`-exclusions:

```text
*_db, !billing_db, analytics_history
```

With a list, a glob, or an exclusion, tables are named `database.table` (for example `globex_db.assets`); with a single plain name they keep their bare table names. Several databases require `data_source` to be `AwsDataCatalog`.

`table_exclude_pattern` is an optional regular expression: tables whose name matches are not indexed, for example `^day_\d{2}`. Changing it removes newly excluded tables, and the agent's selection of them, on the next index.

`s3_output_location` is where Athena writes query results. Leave it blank **only if** your `workgroup` has a default output location configured; otherwise set it to an S3 URI the identity can write to, since Athena cannot return results without one.

The default auth mode, **AWS Default (IAM Role / Instance Profile)**, takes no fields at all — it uses the ambient AWS credentials of the BOW host, which is the right choice when it runs on EC2, ECS, or EKS with an attached role. Otherwise use **AWS Access Keys**, which takes `access_key`, `secret_key`, and `role_arn`.
