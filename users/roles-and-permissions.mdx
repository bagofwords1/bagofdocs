BOW controls access in three layers:

1. **Roles** set what a person can do across the whole organization.
2. **Resource grants** give extra rights on one connection or agent.
3. **Groups** let you give roles and grants to many people at once.

A person's access is everything they get from all three combined. Permissions only add up: nothing takes away a right someone already has.

## Built-in roles

| Role | What it can do |
|---|---|
| **Admin** | Everything in the organization |
| **Member** | Use the workspace: use agents, create and share reports, attach files, see other members, and view and run generated code |
| **App user** | Use the apps shared with them, and nothing else in the workspace. See [App users](#app-users) |

## What every member with the workspace can always do

Every member who has **Use the workspace** can view, create and share reports, attach files to chats, and see the member list. These rights come with **Use the workspace** and can't be removed separately. Editing, deleting or publishing a report is limited to the person who owns it.

A member without **Use the workspace** is an [app user](#app-users) and gets none of these rights.

## Custom roles

<Info>Custom roles require an Enterprise license.</Info>

Go to **Settings → Members → Roles** to build a role from these permissions:

| Area | Permission | Allows |
|---|---|---|
| Workspace | Use the workspace | Open the workspace itself: home, reports, agents. Without it, a member only has the apps shared with them |
| Data & Knowledge | Create agents | Create new agents |
| | Create connections | Add connections; you automatically own what you create |
| | Manage connections | Edit, test, reindex or delete any connection |
| | Manage instructions | Edit instructions on every agent |
| | Manage entities | Manage entities |
| | Manage evals | Manage quality checks |
| | View code | See generated SQL and Python |
| | Run custom code | Edit and run code (also allows viewing it) |
| Members & Access | Manage members | Invite or remove members and change their roles |
| | Manage service accounts | Create API service accounts |
| Settings & Admin | Manage settings | Change organization settings |
| | Manage LLM | Configure models and providers |
| | View audit logs | Read the audit trail |
| | Manage identity providers | Configure SSO, LDAP and SCIM |

<Tip>Members get **View code** and **Run custom code** by default. To hide code from some users, give them a custom role without those two permissions.</Tip>

<Warning>
  The role editor turns **Use the workspace** on for a new role. Keep it on unless the role is meant for app users: a person whose only roles leave it off is an app user. The Admin and Member roles include it.
</Warning>

## App users

An app user is a member of your organization who can open the apps (published dashboards and chat assistants) shared with them, and nothing else in BOW. They can't open reports, agents, connections or settings. Use app users for people who reach BOW through an app you [embed in another product](/guides/embed-chatbot), such as an ERP or a customer portal.

What an app user sees:

- **Your apps**: going to BOW directly opens a launcher at `/apps` with the apps shared with them. An app opens with a back arrow to the launcher.
- **Request full access**: a button on the launcher that asks an admin for the workspace.
- The same apps inside the host product, signed in as themselves.

A member who has the workspace also has the launcher, with an **Open workspace** button.

### Who becomes an app user

- People whose account is created by signing in through a host application whose **New people join as** setting is **App user**. That is the default for a new host application. See [Embed a chat assistant](/guides/embed-chatbot#match-people-by).
- Anyone whose roles all leave **Use the workspace** off.

The **App user** role shows in **Settings → Members**. To give an app user the workspace, change their role in the members list, or add them to a group that holds a role with **Use the workspace**. It is the same account throughout, so nothing has to be moved.

## Resource grants

Resource grants give someone rights on a single connection or agent without making them an admin.

**On a connection**

- **Manage connection**: edit, test, reindex or delete it
- **Create agents**: build agents on top of this connection
- **Manage agents**: manage every agent on this connection

**On an agent**

- **Manage**: full owner rights over this agent (includes everything below)
- **Manage instructions**, **Create entities**, **Manage evals**, **Manage members**

<Note>An organization-wide permission, such as **Manage instructions**, applies to every agent. A **Manage** grant on one agent covers only that agent.</Note>

## Groups

<Info>Groups require an Enterprise license.</Info>

Give a role or grant to a group, and every member of the group gets it. With [SCIM](/enterprise/scim) turned on, groups sync from your identity provider (Entra ID, Okta and others).

## Service accounts

API keys get exactly what their role allows, without the "every member" rights above. New service accounts start with the Member role.

## Project sharing

Shared projects (report folders) use their own **View** or **Manage** access, which you set from the project's Share dialog rather than in roles.

## Examples

<AccordionGroup>
  <Accordion title="Analyst who can't see SQL">
    Create a custom role with **Use the workspace** but without **View code**, and assign it instead of Member.
  </Accordion>
  <Accordion title="Data owner for one connection">
    Keep them as a Member and add a **Manage agents** grant on that connection.
  </Accordion>
  <Accordion title="IT admin without data access">
    Create a custom role with only **Use the workspace**, **Manage members** and **Manage identity providers**.
  </Accordion>
  <Accordion title="Customer who only uses an embedded assistant">
    Set the host application's **New people join as** to **App user**. People who sign in through it can use the apps shared with them and nothing else.
  </Accordion>
</AccordionGroup>
