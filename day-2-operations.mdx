Installing Bag of Words is the easy part. This page is a checklist for the system administrator who keeps it running: what to back up, how to run more than one replica, how to upgrade safely, and what to monitor.

<Info>
New to deployment? Start with [Deployment Options](/install), then come back here before you go live.
</Info>

## Production checklist

| Area | Do this before go-live |
| --- | --- |
| Database | Use PostgreSQL, not the default SQLite. Change the default password. |
| Encryption key | Set `BOW_ENCRYPTION_KEY` explicitly and store it in a secrets manager. |
| Backups | Schedule DB backups, back up the file volumes, the key and `bow-config.yaml`. Test a restore. |
| Image version | Pin a version tag instead of `latest`. |
| TLS and URL | Serve over HTTPS and set `base_url` to the public URL. |
| Reverse proxy | Set `FORWARDED_ALLOW_IPS` if you run behind your own proxy or ingress. |
| Replicas | Run two replicas if you need availability (see [High availability](#high-availability)). |
| Monitoring | Probe `/health`, collect container logs, alert on failed runs. |
| Telemetry | Review anonymous telemetry and disable it if your policy requires. |

## What to back up

Bag of Words keeps its state in five places. Back up all of them. A database backup alone is **not** enough to restore a working system.

| What | Where | Why it matters |
| --- | --- | --- |
| **Database** | PostgreSQL (`BOW_DATABASE_URL`), or `/app/backend/db/app.db` on SQLite | Users, agents, instructions, reports, dashboards, evals, audit logs, scheduled jobs and the stored license key. |
| **Encryption key** | `BOW_ENCRYPTION_KEY` env var, or `/app/backend/data/encryption.key` if it was auto-generated | Encrypts LLM provider API keys, data source credentials and OAuth tokens. |
| **Uploaded files** | `/app/backend/uploads` | Files users uploaded and the connector file cache. |
| **Branding assets** | `/app/backend/branding_uploads` | Custom logos and branding. |
| **Artifact storage** | The path in `BOW_ARTIFACT_STORAGE`, if you use it | Files behind artifact apps. |
| **Configuration** | `bow-config.yaml`, `.env`, `docker-compose.yaml`, `Caddyfile`, Helm values and Secrets | Everything needed to recreate the deployment. |

### The encryption key is the most important thing to back up

<Warning>
If `BOW_ENCRYPTION_KEY` is lost or changed, every stored credential becomes undecryptable. You would have to re-enter every LLM API key, data source credential and OAuth connection. The same key also signs login sessions, so changing it signs every user out. There is currently no key rotation tooling.
</Warning>

- Generate the key once, set it explicitly and keep a copy in your secrets manager (Vault, AWS Secrets Manager, Kubernetes Secret with restricted access, and so on).
- Store it **separately** from your database backups. Anyone holding both can read your credentials.
- If you do not set it, the container generates one and writes it to `/app/backend/data/encryption.key`. That path must be on a persistent volume, and the file must be backed up. On Kubernetes, always set the key through a Secret, because the chart does not provide storage for this file.

```bash
# Generate a key (Fernet, 44 characters)
openssl rand -base64 32 | tr '+/' '-_'
```

### Back up the database

<Tabs>
  <Tab title="Docker Compose">
    ```bash
    # Logical backup of the bundled PostgreSQL
    docker compose exec -T postgres \
      pg_dump -U "$POSTGRES_USER" -Fc "$POSTGRES_DB" \
      > bow-$(date +%F).dump

    # Restore into an empty database
    docker compose exec -T postgres \
      pg_restore -U "$POSTGRES_USER" -d "$POSTGRES_DB" --clean --if-exists \
      < bow-2026-01-01.dump
    ```
  </Tab>
  <Tab title="Managed PostgreSQL">
    Use your provider's automated backups (for example RDS or Aurora automated snapshots with point-in-time recovery, Cloud SQL, Azure Database for PostgreSQL). Set retention to match your recovery objectives.
  </Tab>
  <Tab title="Kubernetes (bundled PostgreSQL)">
    The bundled PostgreSQL is convenient but is a single instance. For production, prefer a managed database or an operator that provides backups. If you keep the bundled one, schedule a `pg_dump` CronJob and ship the dumps off the cluster.
  </Tab>
</Tabs>

Recommendations:

- Take at least a daily backup, and **always take one immediately before an upgrade**. Migrations run automatically on startup and there are no downgrade migrations, so a backup is your rollback path.
- Copy backups off the host or cluster, and keep several generations.
- **Test a restore** into a scratch environment on a schedule. An untested backup is not a backup.
- Do not use SQLite in production. It is a single file on a single node, and it prevents running more than one replica.

### Back up files and configuration

- Snapshot or copy the Docker volumes `uploads_data`, `branding_data` and `app_data` (Compose), or the equivalent persistent volumes.
- Keep `bow-config.yaml`, `.env`, the Compose file, the `Caddyfile` and your Helm values in version control. Keep secrets out of Git and in a secrets manager.
- Do not forget the Caddy certificate volume (`caddy_data`) if you want to avoid re-issuing TLS certificates after a rebuild.

<Note>
On Kubernetes the Helm chart does not mount a volume for uploads or branding by default. Add them with `extraVolumes` and `extraVolumeMounts`, otherwise uploaded files disappear when a pod is rescheduled.
</Note>

## High availability

A single container is a single point of failure, and every deploy or restart interrupts users. For production we recommend **two application replicas** in front of a managed or highly available PostgreSQL.

### Requirements for running two replicas

<Steps>
  <Step title="Use PostgreSQL">
    Multiple replicas cannot share a SQLite file. Use PostgreSQL, ideally managed, with its own backups and failover.
  </Step>
  <Step title="Use the same encryption key everywhere">
    Every replica must receive an identical `BOW_ENCRYPTION_KEY`. Without it each replica generates its own key and cannot read credentials written by the other, and sessions break between replicas.
  </Step>
  <Step title="Share file storage">
    Uploaded files, the file cache and artifact storage live on local disk. Mount a shared (ReadWriteMany) volume for `/app/backend/uploads`, and for `BOW_ARTIFACT_STORAGE` if you use it, so both replicas see the same files.
  </Step>
  <Step title="Budget your database connections">
    Each worker process keeps its own connection pool. The ceiling is:

    ```text
    (BOW_DB_POOL_SIZE + BOW_DB_MAX_OVERFLOW) × workers per replica × replicas
    ```

    The defaults are 20 + 20 per worker, and a replica runs 1 to 4 workers (`UVICORN_WORKERS`). Stock PostgreSQL allows 100 connections, so make sure `max_connections` is above this ceiling, or lower the pool settings. If you exceed the limit you will see failed agent runs rather than a clear pool error.
  </Step>
  <Step title="Put a load balancer in front">
    Use your ingress or load balancer to spread traffic across the replicas, and probe `GET /health`. Chat responses stream over SSE, so disable response buffering and use a long idle timeout (at least a few minutes) on the proxy.
  </Step>
  <Step title="Decide which replica runs background work">
    See the next section.
  </Step>
</Steps>

### Scheduler and background listeners

Scheduled reports and prompts are stored in the database, and runs are de-duplicated across replicas through a shared claim table, so they are safe with several replicas.

Some background work is elected per container, not per cluster: the email (IMAP) poller, the Slack Socket Mode listener, the Google Chat listener and a few housekeeping jobs. With two replicas each one elects its own leader, so these can run twice.

If you use any of those channels, run them on exactly one replica:

| Setting | Effect |
| --- | --- |
| `BOW_SCHEDULER_DISABLED=1` | Turns the scheduler and listeners off on this replica. Set it on all but one replica. |
| `BOW_SCHEDULER_LEADER=1` | Forces this replica to act as the leader. |

<Tip>
The simplest pattern is a second Deployment (or Compose service) from the same image with `BOW_SCHEDULER_LEADER=1`, and the user-facing replicas with `BOW_SCHEDULER_DISABLED=1`. Keep all other settings identical.
</Tip>

### Rolling updates and in-flight work

- Agent runs execute inside the replica that received the request. When a replica is stopped, its in-flight runs end. Give pods a longer `terminationGracePeriodSeconds` than the 30 second default, and deploy during quiet hours.
- If a browser reconnects to a different replica mid-run, it sees the last saved state of the run rather than the live stream.
- Every container applies database migrations when it starts. For releases that change the schema, avoid starting several new replicas at once. Scale to one replica (or use the `Recreate` strategy), let it migrate and become healthy, then scale back up.
- On Kubernetes, enable the PodDisruptionBudget (`podDisruptionBudget.enabled=true`) so node drains never take down both replicas, and spread replicas across nodes or zones.

```yaml
# values.yaml (excerpt)
# Note: the chart always pulls the image (imagePullPolicy: Always), so a
# pinned tag is what protects you from unexpected changes.
replicaCount: 2
image:
  tag: "0.0.587"      # pin a version
podDisruptionBudget:
  enabled: true
terminationGracePeriodSeconds: 120
config:
  secretRef: bow-secrets   # holds BOW_ENCRYPTION_KEY, BOW_DATABASE_URL, ...
  forwardedAllowIps: "*"   # only if the ingress is the sole peer
```

## Upgrades

There are two ways to keep Bag of Words up to date:

- **Planned upgrades**: you choose the version, back up, upgrade and verify. Recommended for production.
- **Automatic updates** (Docker Compose only): a cron job pulls new images on a schedule and restarts only the containers that changed. Good for evaluation, internal or low-risk instances. See [Automatic updates with Docker Compose](#automatic-updates-with-docker-compose).

### Before you upgrade

- **Pin versions.** Images are published as `bagofwords/bagofwords:<version>`, `<version>-<date>` and `latest`. The Compose file and Helm chart default to `latest` with always-pull. Override this in production.
- **Migrations are automatic.** On start, the container runs the database migrations and exits if they fail after three attempts. Because there is no downgrade path, rolling back means restoring the pre-upgrade database backup and redeploying the previous image tag.
- **Only the latest release gets security fixes**, so plan to upgrade regularly (see the [operations calendar](#routine-operations-calendar)).

### Planned upgrade

<Steps>
  <Step title="Read the release notes">
    Review the [release notes](https://github.com/bagofwords1/bagofwords/blob/main/CHANGELOG.md) (also available in the app under **What's New**) for breaking changes.
  </Step>
  <Step title="Back up">
    Take a database backup and confirm your encryption key, file volumes and config are saved. See [What to back up](#what-to-back-up).
  </Step>
  <Step title="Test first">
    If you can, restore the backup into a staging environment and upgrade it first.
  </Step>
  <Step title="Upgrade to a pinned version">
    Change the image tag to the new version number and redeploy. Do not rely on `latest`, which can change underneath you on any restart. The commands for each deployment type are below.
  </Step>
  <Step title="Verify">
    Check that `/health` responds, you can sign in, a data source connects, and a simple question gets answered.
  </Step>
</Steps>

<Tabs>
  <Tab title="Docker Compose">
    Set the new tag in `docker-compose.yaml`:

    ```yaml
    services:
      bagofwords:
        image: bagofwords/bagofwords:0.0.587   # the new version
    ```

    Then pull and recreate:

    ```bash
    docker compose pull
    docker compose up -d
    docker compose logs -f bagofwords   # watch the migrations and startup
    ```

    `docker compose up -d` only recreates containers whose image or configuration changed. PostgreSQL and Caddy keep running.
  </Tab>
  <Tab title="Kubernetes (Helm)">
    ```bash
    helm repo update
    helm upgrade <release> bow/bagofwords -n <namespace> \
      --reuse-values \
      --set image.tag=0.0.587
    kubectl rollout status deployment/<release> -n <namespace>
    ```

    For releases that change the schema, scale to one replica first (or use the `Recreate` strategy) so only one pod runs migrations. See [Rolling updates and in-flight work](#rolling-updates-and-in-flight-work).
  </Tab>
  <Tab title="Single Docker container">
    ```bash
    docker pull bagofwords/bagofwords:0.0.587
    docker stop bagofwords && docker rm bagofwords
    # Re-run your original `docker run` command with the new tag,
    # keeping the same volumes and environment variables.
    ```
  </Tab>
  <Tab title="Air-gapped">
    Download and verify the new version's bundle, load its images as described in the README inside `bagofwords-airgap/`, update the image tag, then start without pulling:

    ```bash
    docker compose up -d --pull never
    ```

    See [Air-gapped downloads](/install#air-gapped-downloads).
  </Tab>
</Tabs>

### Rolling back

1. Stop the application.
2. Restore the database backup you took before the upgrade.
3. Set the image tag back to the previous version and redeploy.

Redeploying an older image against an already migrated database is not supported. Always restore the database first.

### Upgrade notes

- **Helm chart 2.0.0** changed the Deployment selector labels. Upgrading from chart 1.x fails with `field is immutable: spec.selector`. Delete the Deployment (`kubectl delete deployment <release> -n <namespace>`) and run the upgrade again.

### Automatic updates with Docker Compose

For Docker Compose installs, a small script keeps the deployment on the newest image. It is meant to run from cron. Each run:

1. Pulls the latest images for every service in the Compose file.
2. Recreates only the containers whose image changed. Services with unchanged images keep running without interruption. The updated containers restart, so expect a short interruption of Bag of Words while the new container starts and runs migrations.
3. Removes dangling images to free disk space.

The script follows the tags in your Compose file. With `bagofwords/bagofwords:latest` it moves to every new release. With a pinned tag such as `0.0.587` it only picks up a rebuild of that same tag, so to move to a new version you still change the tag yourself.

<Warning>
Automatic updates skip the review, backup and testing steps of a [planned upgrade](#planned-upgrade). Migrations run as soon as the new container starts, and there is no downgrade. Before enabling this:

- Schedule database backups to run **before** each update window (for example, a backup cron job 30 minutes earlier). See [Back up the database](#back-up-the-database).
- Know that the script prunes the previous image once it is untagged. To roll back you will pull the previous version by its version tag and restore the database backup.
- For business-critical production, prefer pinned versions and planned upgrades.
</Warning>

#### The script

Save this as `version-auto-update.sh` on the Docker host, for example in `/opt/bagofwords/`. It is also available in the repository at [`scripts/version-auto-update`](https://github.com/bagofwords1/bagofwords/tree/main/scripts/version-auto-update).

```bash version-auto-update.sh
#!/usr/bin/env bash
set -euo pipefail

usage() {
  echo "Usage: $0 -c <compose-command> -f <docker-compose-file>"
  echo "  -c  Docker compose command (e.g. 'docker compose' or 'docker-compose')"
  echo "  -f  Path to docker-compose.yaml file"
  exit 1
}

COMPOSE_CMD=""
COMPOSE_FILE=""

while getopts "c:f:" opt; do
  case "$opt" in
    c) COMPOSE_CMD="$OPTARG" ;;
    f) COMPOSE_FILE="$OPTARG" ;;
    *) usage ;;
  esac
done

[[ -z "$COMPOSE_CMD" || -z "$COMPOSE_FILE" ]] && usage

if [[ ! -f "$COMPOSE_FILE" ]]; then
  echo "Error: file not found: $COMPOSE_FILE"
  exit 1
fi

COMPOSE="$COMPOSE_CMD -f $COMPOSE_FILE"

echo "$(date '+%Y-%m-%d %H:%M:%S') Pulling latest images..."
$COMPOSE pull

echo "$(date '+%Y-%m-%d %H:%M:%S') Recreating containers with updated images..."
$COMPOSE up -d

echo "$(date '+%Y-%m-%d %H:%M:%S') Removing unused images..."
docker image prune -f

echo "$(date '+%Y-%m-%d %H:%M:%S') Done."
```

#### Usage

```bash
./version-auto-update.sh -c <compose-command> -f <docker-compose-file>
```

| Flag | Description | Example |
| --- | --- | --- |
| `-c` | Docker Compose command | `"docker compose"` or `"docker-compose"` |
| `-f` | Path to `docker-compose.yaml` | `/opt/bagofwords/docker-compose.yaml` |

```bash
# Docker Compose v2 plugin
./version-auto-update.sh -c "docker compose" -f /opt/bagofwords/docker-compose.yaml

# Legacy standalone docker-compose
./version-auto-update.sh -c "docker-compose" -f /opt/bagofwords/docker-compose.yaml
```

Run it once by hand to confirm it works before you schedule it.

#### Schedule it with cron

<Steps>
  <Step title="Make the script executable">
    ```bash
    chmod +x /opt/bagofwords/version-auto-update.sh
    ```
  </Step>
  <Step title="Open the crontab">
    ```bash
    # For the current user (must be able to run docker)
    crontab -e

    # For root, if Docker requires root access
    sudo crontab -e
    ```
  </Step>
  <Step title="Add the job">
    This runs twice a day, at 6:00 and 18:00, and appends the output to a log file. Use full paths, because cron runs with a minimal environment.

    ```text
    0 6,18 * * * /opt/bagofwords/version-auto-update.sh -c "docker compose" -f /opt/bagofwords/docker-compose.yaml >> /var/log/version-auto-update.log 2>&1
    ```

    Save and exit the editor.
  </Step>
  <Step title="Verify the job">
    ```bash
    crontab -l
    ```
  </Step>
</Steps>

Other schedules:

| Schedule | Cron expression |
| --- | --- |
| Twice a day (6:00 and 18:00) | `0 6,18 * * *` |
| Every 6 hours | `0 */6 * * *` |
| Once a day at midnight | `0 0 * * *` |
| Every hour | `0 * * * *` |

<Tip>
Pick a quiet time, since the Bag of Words container restarts whenever a new image is found. Once a day outside working hours is enough for most teams.
</Tip>

#### Logs

Every run appends timestamped output to `/var/log/version-auto-update.log`:

```bash
tail -f /var/log/version-auto-update.log
```

After an update, check `/health` and the container logs (`docker compose logs bagofwords`) to confirm migrations finished.

#### Notes

- Cron jobs persist across reboots, and the cron daemon starts automatically on boot.
- The user running the job needs permission to run Docker, either root or a member of the `docker` group.
- The log file must be writable by that user. If you run the job as a non-root user, point the log at a path it owns.

## Monitoring

### Health checks

`GET /health` returns `{"status":"ok"}`. It confirms the process is running but does **not** check the database. Use it for liveness and load balancer probes, and add your own database monitoring alongside it. The container image and Helm chart already use it.

### Logs

The application logs JSON lines to stdout (errors to stderr). Collect them with your platform's log pipeline (Docker logging driver, Fluent Bit, Promtail, CloudWatch, and so on) and set a retention period. Nothing is written to log files inside the container.

### Traces

OpenTelemetry tracing is built in and off by default. Enable it in `bow-config.yaml`:

```yaml
otel:
  enabled: true
  service_name: bagofwords-backend
  traces_endpoint: http://otel-collector:4317
  protocol: grpc
```

### What to alert on

- `/health` failing, or containers restarting repeatedly.
- Database: connection count approaching `max_connections`, disk usage, replication lag, failed backups.
- Disk usage on the uploads and artifact volumes.
- Spikes in failed agent runs. Use [Runs and traces](/observe-and-govern/runs-and-traces) to investigate.
- LLM spend and errors. Track them in [Usage, cost and quality](/observe-and-govern/usage-cost-quality) and set [quotas](/observe-and-govern/quotas-and-usage-limits).
- TLS certificate expiry, if you manage certificates yourself.

### Audit logs

[Audit logs](/observe-and-govern/audit-logs) record administrative activity. On the enterprise plan you can stream them to your SIEM (Datadog, Splunk, Microsoft Sentinel, S3, GCS, a webhook or syslog) so they are retained outside the application database.

## Security hardening

- **HTTPS everywhere.** Keep Caddy or your ingress terminating TLS, and set `base_url` to the public `https://` URL. It is used for SSO redirects, and SAML requires HTTPS.
- **Change default credentials.** Replace the sample PostgreSQL password (`bowpassword` in the Compose file) and restrict who can reach the database port. Do not publish PostgreSQL to the internet.
- **Keep secrets out of config files.** Reference them as `${VAR}` in `bow-config.yaml` and inject them from Docker secrets, a Kubernetes Secret (`config.secretRef`) or your secrets manager.
- **Set `FORWARDED_ALLOW_IPS` correctly.** Behind a proxy or ingress, the default (`127.0.0.1`) makes every visitor look like the same client, which breaks per-client rate limiting. Set it to your proxy's address.
- **Use SSO.** Configure [SSO](/sign-in-and-sso), set `auth.mode` to `sso_only` if you want to disable local passwords, and review who has admin roles. Disable open sign-ups with `allow_uninvited_signups: false`.
- **Limit network access.** Enable the chart's NetworkPolicy and allow outbound traffic only to your LLM providers, data sources and identity provider. Use `HTTPS_PROXY` and `NO_PROXY` if egress goes through a proxy.
- **Least-privilege data access.** Give each data source a read-only database user, and use [row-level security](/bow-fast/row-level-security) where users should see different data.
- **Telemetry.** Anonymous product telemetry is enabled by default. Set `telemetry.enabled: false` in `bow-config.yaml` (Helm: `config.telemetryEnabled=false`) if your policy requires it, and always in air-gapped environments.
- **Scan and patch.** Pull updated images regularly, scan them in your registry, and patch the host and PostgreSQL on a schedule.

## Capacity and cost

- **Size for concurrency.** Each worker runs up to `BOW_MAX_CONCURRENT_AGENTS` agent runs at once (default 12), and extra runs queue. Watch CPU and memory under real load and adjust workers (`UVICORN_WORKERS`) and resources. The Helm chart requests 2 CPUs and 900Mi by default and sets no memory limit.
- **Control LLM spend.** Set [usage quotas](/observe-and-govern/quotas-and-usage-limits), and review cost regularly. Keep a second model configured, or use fallback on the enterprise plan, so an outage at one LLM provider does not stop your users.
- **Protect your data sources.** Add rate limits (enterprise) or use a read replica for analytics so heavy questions cannot slow your production systems.
- **Retention.** Step payloads are purged automatically (14 days by default). Plan for database growth from reports, traces and audit logs, and monitor disk space.

## Routine operations calendar

| Frequency | Task |
| --- | --- |
| Daily | Confirm the backup succeeded. Glance at failed runs and LLM errors. If automatic updates are on, check `/var/log/version-auto-update.log`. |
| Weekly | Review audit logs and usage. Check disk and database size. |
| Monthly | Upgrade to the latest release after testing. Patch hosts and PostgreSQL. Review user access and admin roles. |
| Quarterly | **Restore test** from backup into a scratch environment. Review secrets, API keys and service accounts. Review quotas and capacity. |
| Before every upgrade | Back up the database and confirm you have the encryption key. |

## Disaster recovery in short

1. Provision a new environment and deploy the same image version you were running.
2. Restore the PostgreSQL backup.
3. Restore the file volumes (`uploads`, `branding_uploads`, artifact storage).
4. Supply the **original** `BOW_ENCRYPTION_KEY` and your `bow-config.yaml`.
5. Start the application, point DNS at it, and verify sign-in, a data source and a test question.
